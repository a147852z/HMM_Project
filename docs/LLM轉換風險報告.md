# LLM 資料轉換可能遇到的問題

> 日期：2026-11-17
> 依據：K 的轉換流程設計（`kcore/conversion/`），以及 2026-11-17 用 `google/gemma-4-26b-a4b` 對 5 份示意文件的實測（`docs/LLM轉換測試報告.md`）。
> 標示「**實測**」的項目在測試中實際發生過；其餘是依設計與經驗推估、尚未實際遇到的風險。

## 1. 摘要

LLM 轉換的目的是把格式不固定的工廠紀錄整理成 K 的演變序列。它最大的風險不是「轉不出來」，而是「轉出看起來合理、但內容錯誤的資料」。這類錯誤一旦通過審核進入訓練資料，會直接影響 HMM 學到的規律。

目前的保護有兩層：K 的自動驗證，以及人工審核。自動驗證只能抓到一部分錯誤（見第 6 節），所以**人工審核不能省略**，也是目前最重要的品質關卡。

## 2. 輸入資料的問題

| 問題 | 說明 | 目前的處理 | 建議 |
| --- | --- | --- | --- |
| 非文字檔 | Excel、Word、PDF、掃描圖片無法直接上傳 | 上傳時拒絕，請使用者先轉成文字 | 依真實資料的格式加上轉換步驟；掃描文件需要 OCR，錯字會更多 |
| 文件太長 | 超過模型一次能讀的長度時，後半段會被忽略或截斷 | 單檔上限 20 萬字，但模型實際能讀的長度更短 | 依製令或日期分段；分段後一張製令可能跨兩段，需要合併規則 |
| 一張製令分散在多份文件 | 例如週一的筆記與週三的會議紀錄都在改同一張製令 | **目前不支援**：每份文件獨立轉換，同一製令會變成兩條序列，或因識別碼不同而重複 | 需要「依製令編號合併跨文件序列」的功能，這是接真實資料前就要處理的設計問題 |
| 文字品質 | 錯字、縮寫、口語、「那一站」這類指代、跳躍或倒敘的敘述 | 無 | 在案例提示詞中補充該場域的常用縮寫與站點別名 |
| 改了又改 | 同一站先加後刪、參數改兩次，或口頭決議後又推翻 | 無 | 測試集需要加入這類文件，確認 LLM 只記錄最終確認的修改順序 |
| 敏感資訊 | 客戶名稱、人名、金額會被送進 LLM，原文也存在資料庫 | 使用本地模型，資料不會離開內網；原文完整保存 | 上傳前去識別化；確認資料庫的存取權限 |

## 3. LLM 理解錯誤

| 問題 | 實測 | 說明 | 目前的處理 |
| --- | --- | --- | --- |
| 漏掉連線 | **實測**：12 條序列中 5 條 | 刪除中間站點後沒有接起前後兩站；新增平行分支時拿掉原有連線 | 格式說明已補上規則（效果有限）；結構檢查會提醒審核者，實測 5/5 都有提醒 |
| 把「改了什麼」當成「為什麼改」 | **實測**：第 1 輪 3 次 | 例如把「加工改用 CNC-2 機台」當成原因，並標為原文記載 | 格式說明已釐清，之後沒有再發生 |
| 捏造不存在的資訊 | **實測**：原文沒寫年份，LLM 自行補上 2024 | 也可能捏造參數值、站點或修改 | 格式說明要求沒有年份時填 null；其他捏造目前抓不到 |
| 活動類型對錯 | 未發生 | 同一個站點可能被歸到不同類型，例如「去毛邊」歸成加工或清洗 | 提示詞列出允許的類型；類型對錯 K 無法自動判斷 |
| 提議與採用混淆 | 未發生（會議紀錄測試通過） | 把被否決、待確認的提議當成已採用的修改 | 提示詞要求只記錄確認採用的修改 |
| 漏掉某次修改 | 未發生 | 長文件或敘述分散時，可能少記一次修改 | 抓不到；只能靠審核者對照原文 |
| 修改順序錯誤 | 未發生 | 倒敘或時間不明的紀錄可能排錯順序 | 抓不到 |
| 同一站點在不同版本換了代號 | 未發生 | 會被當成「刪除再新增」，修改類型就錯了 | 格式說明要求同一站點使用相同代號 |
| 分支語意不明 | 未發生 | 平行分支是「兩條都做」還是「擇一」，AoV 的定義尚未決定 | 待決定事項（設計文件第 6 節） |

## 4. 輸出格式問題

| 問題 | 實測 | 目前的處理 |
| --- | --- | --- |
| 同時給「修改差異」與「修改後的完整流程」 | **實測**：第 1 輪 10 次中 7 次因此被判錯 | 已改為以完整流程為準，兩者不一致時提醒審核者 |
| 回應不是合法 JSON，或輸出被截斷 | 未發生 | 轉換標為失敗並保留原始回應；可以在審核畫面手動修正草稿 |
| 推理模型輸出思考過程 | 未發生 | 已自動移除 `<think>` 區塊與程式碼框 |
| 服務不支援結構化輸出 | 未發生（LM Studio 支援） | 轉換設定可以關閉結構化輸出，改為從一般回應擷取 JSON |

## 5. 穩定性與效能

| 問題 | 實測 | 說明 | 建議 |
| --- | --- | --- | --- |
| 結果不穩定 | **實測**：溫度設為 0，同一份文件兩次結果仍不同 | 同樣的資料轉兩次可能一對一錯 | 不要假設重新轉換會得到一樣的結果；重要文件可以轉兩次比對 |
| 速度 | **實測**：每份 20～120 秒 | 大量文件時需要排隊；目前背景轉換一次處理一份 | 批次轉換時錯開時間，或使用較小的模型 |
| 模型更換 | — | 換模型或模型更新後，同類文件的轉換方式可能改變 | 轉換設定記錄了模型名稱與提示詞版本；換模型前先跑測試集比較 |
| 伺服器無法連線 | — | LM Studio 關閉或網路中斷 | 轉換會標為失敗並保留紀錄；轉換設定頁可以測試連線 |

## 6. K 的自動驗證抓得到與抓不到的錯誤

| 抓得到（會擋下或提醒） | 抓不到（只能靠人工審核） |
| --- | --- |
| 流程有循環、連線指向不存在的站點 | 活動類型對應錯誤 |
| 修改後流程斷開、某站沒有上一站或下一站 | 漏掉某次修改 |
| 標為「原文記載」的原因在原文中找不到 | 修改順序錯誤 |
| 同一份文件重複匯入 | 捏造的參數值或站點 |
| 修改差異與完整流程不一致 | 原因引文確實在原文中，但其實不是原因 |
| 格式錯誤、缺少必要欄位 | 修改歸到錯誤的製令 |

右欄的錯誤會讓資料「看起來正常」，是最需要注意的部分。

## 7. 對 HMM 訓練的影響

- **錯誤會變成雜訊**：審核漏掉的錯誤會進入訓練資料。少量隨機錯誤影響不大，但**系統性錯誤**影響很大。例如 LLM 每次刪除站點都漏接連線，模型就會學到「刪除站點後流程會斷開」這種不存在的規律。
- **轉換方式改變會讓資料前後不一致**：提示詞或模型改版後，同類文件的轉換結果可能不同，新舊資料混在一起訓練。目前每條序列都記錄了提示詞版本與模型，事後可以追查。
- **審核疲勞**：如果大部分草稿都需要修正，審核者容易只看大概就核准。實測約 4 成的序列需要修正最終流程。

## 8. 建議的處理順序

1. **取得真實紀錄樣本**：兩三份去識別化的真實文件，加入測試集（文件＋標準答案）。這是判斷實際品質的唯一方法。
2. **決定跨文件的製令如何合併**：真實資料很可能一張製令分散在多份紀錄裡，這會影響資料表與轉換流程的設計。
3. **維持每份草稿人工審核**，不要開放未審核直接匯入。
4. **比較其他模型**：伺服器上有 `gemma-4-31b`、`qwen3.6-35b` 等，用同一套測試集比較準確率與速度。
5. **試試只輸出完整流程**：這次漏連線的錯誤多出現在 LLM 描述「修改差異」時；改成每一步都輸出完整流程，由程式計算差異，可能減少這類錯誤。
6. **長期追蹤品質**：記錄每份草稿被審核者修改的比例與類型。修改比例上升時，代表文件類型變了或模型退化。

## 9. 建議追蹤的指標

| 指標 | 用途 |
| --- | --- |
| 草稿通過驗證的比例 | 格式與結構層的品質 |
| 審核時被修改的草稿比例，以及修改的類型 | 實際轉換品質；最重要的指標 |
| 結構提醒出現的比例 | 漏連線等錯誤的頻率 |
| 原因被降級為「LLM 推論」的比例 | 引文捏造的頻率 |
| 每份文件的轉換時間、失敗率 | 服務是否穩定 |
| 測試集的準確率（每次換模型或改提示詞時） | 防止改版後品質下降 |
