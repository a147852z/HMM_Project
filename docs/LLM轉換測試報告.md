> 日期：2026-11-17

> 測試集：`k_core/backend/evaldata/llm_conversion/`（5 份**人工撰寫的示意文件**與標準答案 `expected.json`，不是真實工廠紀錄）
> 腳本：`k_core/backend/scripts/llm_conversion_eval.py`；最後一輪原始數據：`docs/llm_conversion_eval.json`

## 1. 測試方式

走 K 實際的轉換流程：建立轉換設定 → 上傳文件 → 本地 LLM 產生 JSON 草稿 → K 驗證。再與標準答案逐項比對。每份文件轉換 2 次，共 10 次。轉換結果留在資料庫的 `LLMTEST` 案例中，可以在網頁「轉換與審核」分頁檢視，沒有核准匯入。

| 文件 | 寫法 | 測試重點 |
| --- | --- | --- |
| a_engineer_notes.txt | 工程師手寫筆記 | 插入、改參數、刪除中間站點；有一筆沒寫原因 |
| b_change_table.csv | 表格 | 表格欄位解讀；部分列沒寫原因 |
| c_versions.txt | 各版本的完整流程 | 平行分支 |
| d_meeting.txt | 會議紀錄 | 有被否決的提議、與流程無關的內容 |
| e_weekly_summary.txt | 一份文件兩張製令 | 拆成兩條序列 |

比對項目：序列數、初始流程、最終流程（活動類型與連線完全相同）、每一次修改的結構類型、修改原因的來源（原文有寫 → human；沒寫 → null 或 llm）。

## 2. 三輪結果

| 項目 | 第 1 輪 | 第 2 輪 | 第 3 輪 |
| --- | --- | --- | --- |
| 通過 K 驗證 | 3/10 | **10/10** | **10/10** |
| 序列數正確 | 12/12 | 12/12 | 12/12 |
| 初始流程正確 | 12/12 | 12/12 | 12/12 |
| 最終流程正確 | 3/12 | 6/12 | **7/12** |
| 修改類型正確 | 7/24 | **24/24** | 23/24 |
| 修改原因來源正確 | 7/24 | **24/24** | **24/24** |
| 把沒寫的原因標成「原文記載」 | 3 次 | 0 | 0 |
| 最終流程錯誤時有提醒審核者 | — | — | **5/5** |
| 平均每份文件耗時 | 54 秒 | 23 秒 | 47 秒 |

每一輪之間做的修改（都是 K 的通用改進，不是只針對這 5 份文件）：

- **第 1 → 2 輪**
  - LLM 同時給了「修改差異」與「修改後的完整流程」時，改為以完整流程為準，由程式計算差異。原本這種情況會被判為錯誤，是第 1 輪 7 次失敗的主因。兩者不一致時會提醒審核者。
  - 固定格式說明補上：修改原因是「為什麼要改」，不是「改了什麼」；原文的時間沒有年份時填 null。
- **第 2 → 3 輪**
  - 新增結構檢查：修改後流程斷成多段，或某一站突然沒有下一站、沒有上一站時，提醒審核者。
  - 固定格式說明補上：刪除中間站點要接起前後兩站；新增分支時不要刪除原有的連線。

## 3. 結論

**做得好的地方**

- 文件結構都讀得懂：序列拆分、初始流程、被否決的提議、無關內容，10 次全對。
- 第 2 輪起，修改類型與原因來源幾乎全對，不再把「改了什麼」誤當成原因。

**仍然會錯的地方**

- **漏掉連線**：刪除中間站點後沒有接起前後兩站，或新增平行分支時拿掉原有的連線。補上提示規則後只多對了 1 次，提示詞對這類錯誤的效果有限。
- 好消息是**結構檢查抓到了全部 5 次錯誤**，而且沒有誤報正確的結果。審核者在網頁上會看到「某站修改後沒有下一站，可能漏了連線」的提醒。所以這類錯誤目前的處理方式是「交給審核者修正」，這正是審核流程存在的目的。

**速度**：每份約 20～50 秒，偶爾超過 100 秒，視伺服器負載而定。

## 4. 限制

- 文件是我寫的，寫法比真實紀錄整齊；真實紀錄可能有錯字、縮寫、跳躍的敘述。
- 第 2、3 輪的修改是看過這 5 份文件的錯誤後才做的，所以這份測試集上的分數偏樂觀。
- 只測了一個模型。

**下一步最需要的是真實的工廠紀錄**，哪怕只有幾份，才能知道實際的轉換品質。測試集的格式（文件＋`expected.json`）可以直接加入新的文件。
