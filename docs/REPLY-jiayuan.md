## 一、確認我們的理解

### 確認 1：11/17 包的錯誤類型，「`error_types` 只有 `ok`」能不能當成「這一版通過」

對程式題可以這樣用，這也是我們的建議（見 Q11），但你列的條件要補幾個前提，而且它和判分器的「通過」（`judge_v1i`）不是同一件事。

每個 try 的錯誤類型由產生更新包的程式依判分檔的欄位算出，精確條件如下：

| 類型 | 條件 | 哪些 metric 會檢查 |
|---|---|---|
| `not_executable` | 判分檔的 `executable` 為 false。出現時只回這一個類型，不再判其他類型（此時 P、R、預測數是補的 0） | 全部 |
| `count_over` | 預測數 > `gt_count`（嚴格大於，沒有容差） | `count_only`、`count_and_boxes`，且 `gt_count` 有值 |
| `count_under` | 預測數 < `gt_count` | 同上 |
| `boxes_extra` | `n_pred` ≥ 1 且 P < 0.8（一個框都沒畫時不算框多） | `count_and_boxes`、`detect_only`，且 `gt_boxes` 有值 |
| `boxes_missed` | 正解框數 ≥ 1 且 R < 0.8（正解沒有框時不算框漏） | 同上 |
| `ok` | 以上都沒有 | |
| `unjudged` | 沒有正解可比（照片題） | |

門檻是 P、R 各 0.8，「小於 0.8 才算錯」，所以 P = 0.8 或 R = 0.8 剛好算過。P 與 R 取自判分檔，配對方式是 IoU ≥ 0.5 的一對一配對，P = 配對數 ÷ 預測框數，R = 配對數 ÷ 正解框數，這裡沒有套用忽略區，也不看類別。預測數優先用判分檔的 `count`（流程圖數字輸出埠的值），沒有這個欄位才用 `n_pred`（偵測框數），每列的 `count_source` 記錄用的是哪一個。`count_only` 題只比數量，`tries.jsonl` 裡這類題 `ok` 的列 P = R = 0.0 是補值，不是框錯。`detect_only` 題只比框，`count_and_boxes` 題兩者都比。一個 try 可以同時有多個類型，例如 `count_under` 加 `boxes_missed` 有 202 列，`count_over` 加 `boxes_extra` 有 153 列，`not_executable` 與 `ok` 則一定單獨出現。2,023 個程式題 try 的類型數量是 `ok` 1,131、`count_over` 340、`count_under` 390、`boxes_extra` 379、`boxes_missed` 423、`not_executable` 62，和報告第 11 行一致。

## 二、10/13 材料包

### Q1：`v0`、`v1i`、`v1c`、`v1s` 的條件與門檻

`v1i`、`v1c`、`v1s` 的門檻都是 P ≥ 0.8 且 R ≥ 0.8，三者的差別在「多出來的框能不能被忽略區吸收」與「要不要看類別」，不在門檻高低。`v0` 是另一套舊判準，只要求每個正解框都配到（R = 1），不看精確率。你推測的「`v1i` 約 P ≥ 0.6 就成立」不成立，原因是判分檔裡記的 `P` 和 `v1i` 用的 P 不是同一個數。

以下是有框題（`metric` 為 `detect_only` 或 `count_and_boxes`）的定義：

| 標記 | 配對方式 | 成立條件 |
|---|---|---|
| `v0` | 貪婪配對：每個正解框依序挑 IoU 最大且 ≥ 0.5、還沒被用過的預測框 | 全部正解框都配到（FN = 0），不看多出來的預測框 |
| `v1i` | 一對一最大配對（匈牙利法），IoU ≥ 0.5 | 沒配到的預測框若和忽略區的小框 IoU ≥ 0.5，或落在 crowd 區內的比例（IoA）≥ 0.5，就被吸收、不算進分母。P = 配對數 ÷（預測框數 − 被吸收數），R = 配對數 ÷ 正解框數，P ≥ 0.8 且 R ≥ 0.8 才成立。不看類別 |
| `v1c` | 同 `v1i` | 同 `v1i`，另外加類別限制：預測框的 label 是 COCO 80 類之一、但不是題目類別時，不能配對也不能被吸收，照樣算進分母。沒有 label 或 label 不屬 COCO 類別（例如輪廓法產生的框）不扣分。題目類別由題號前綴決定，例如 `coco_car_*` 是 car |
| `v1s` | 同 `v1i` | 同 `v1i`，但不用忽略區，P = 配對數 ÷ 全部預測框數，這是四者中最嚴格的 |

忽略區是 COCO 原始標註裡屬於題目類別、但沒有放進正解的框（非 crowd 的當小框，crowd 的當 crowd 區），忽略區檔不在包裡，IoU 門檻在 41 題都是 0.5。判分檔每個 try 記的 `P`、`R`、`K` 是用不套忽略區、不看類別的方式算出來的，也就是 `v1s` 的口徑，這是你看到 `P` = 0.75 而 `v1i` 為真的原因。`count_only` 題四個標記一律相同，都等於「數量在容差內」（見 Q4）。

四者的關係是：`v1s` 成立則 `v1i` 必成立，因為忽略區只會讓分母變小，`v1c` 成立則 `v1i` 也必成立，因為類別限制只會讓配對變少。包內 956 個 try 驗證，沒有任何一個 `v1s` 成立而 `v1i` 不成立，`v1i` 與 `v1c` 在 956 個 try 裡完全一致。`v0` 和 `v1` 系列沒有包含關係，有 124 個 try 是 `v0` 成立、`v1i` 不成立（正解框都配到，但多報太多），也有 30 個 try 是 `v1i` 成立、`v0` 不成立（R 介於 0.8 與 1 之間）。

至於和 11/17 包錯誤類型的關係，10/13 這批成績沒有「數量完全相等」這個條件。當時的判分程式對有框題完全不看數量，`count_and_boxes` 題和 `detect_only` 題判法相同，P ≥ 0.8、R ≥ 0.8 對應的是 `v1i`、`v1c`、`v1s`，差別只在 P 的分母。「數量完全相等」是 10/23 之後才用在 11/17 包程式題的判準，不適用 10/13 包。

以 `teachers/codex/tasks/coco_car_124798` 的 try 1 驗算（`detect_only`，類別 car，正解 6 框，忽略區 3 個小框）：重播得到 8 框、全部標成 car，一對一配到 6 框，所以 `K` = 6。`v1s` 的 P = 6 ÷ 8 = 0.75 < 0.8，不成立，這就是判分檔裡的 `P` = 0.75。`v1i` 則是沒配到的 2 框分別和忽略區的小框 IoU ≥ 0.5、被吸收，P = 6 ÷（8 − 2）= 1.0，R = 6 ÷ 6 = 1.0，成立。8 框都是 car，所以 `v1c` 同樣成立，6 個正解框都配到，`v0` 也成立。同一題其他 try 也對得上你觀察到的現象，try 7 的 `P` = 0.6（10 框），吸收 3 框後是 6 ÷ 7 = 0.857，`v1i` 成立，try 3 的 `P` = 0.5455（11 框），吸收 3 框後是 6 ÷ 8 = 0.75，不成立，try 8 同樣 11 框但只吸收 2 框，6 ÷ 9 = 0.667，也不成立。所以看起來像「P 約 0.6 以上就過」，其實門檻始終是 0.8。

### Q5：`K` 是什麼，為什麼同一題不同 try 的 `K` 不同

`K` 不是正解框數，是這一次的預測框和正解框一對一配對成功的數量（TP），所以每個 try 都可能不同。正解框數可以用 `K` ÷ `R` 推回（`R` > 0 時），包內 956 個 try 驗證，有框題 `K` = `P` × `n_pred`、`R` = `K` ÷ 正解框數，沒有例外。

### Q8：`attempts.jsonl` 的 `ok` 怎麼判斷

程式題的 `ok` 是「該筆解題紀錄任一個 try 的 `v1i` 為真」，也就是判分檔的 `any_ok`，和 `error_types`、`stop_reason` 都無關。照片題沒有正解，它的 `ok` 是「有 try 檔、最後一個 try 能執行，而且 `stop_reason` 是 `satisfied`」，也就是解題者自己宣告滿意，不代表答對。

照片題的「能執行」是指沒有 `validator_errors` 且 `exec_error` 為空。沒有任何 try 檔的程式題解題紀錄，`ok` 是 null。

重算結果如下。程式題有 try 的解題紀錄 1,302 筆，`ok` 等於「任一 `judge_v1i` 為真」1,302/1,302 相符，其中 `ok` 為真 1,074 筆、為假 228 筆，另有 922 筆沒有 try、`ok` 為 null。`ok` 為真的 1,074 筆中，有 12/1,074 筆沒有任何一個 try 的錯誤類型是 `ok`（就是 Q7 的 12 筆），有 211/1,074 筆的 `stop_reason` 不是 `satisfied`（`satisfied` 863 筆，其餘是 null 184、`max_rounds` 16、`error` 10、`unchanged` 1），其中 null 是因為 Claude 解題者那條線沒有 `traj.json`，不代表不滿意。`ok` 為假的 228 筆中，有 `ok` 類型 try 的是 0/228，解題者宣告滿意、判分器卻說沒過的有 54/228。反過來看，宣告滿意但沒有任何 `ok` 類型 try 的有 59 筆。

照片題有 try 的 1,293 筆，上面的公式和 `ok` 欄 1,293/1,293 相符，`ok` 為真 716 筆、全部是 `satisfied`，`ok` 為假 577 筆（`max_rounds` 481、`safety_flag` 66、`unchanged` 24、`error` 6）。

以題目計，有 try 的程式題 1,169 題，任一解題者 `ok` 為真的 1,074 題，和報告「95/1169 沒解開」一致，有 `ok` 類型 try 的則是 1,062 題。

### Q9：`attempts.jsonl` 的 `sealed_try_mismatch`

它比的是「判分檔裡記的 try 數」是否等於「解題資料夾裡 `try*.json` 的檔數」，用來標示判分檔和 try 檔對不上的情況，例如判分之後才多寫了 try，或 try 檔被刪掉。這份快照裡沒有任何一筆是 true。

| 值 | 筆數 | 情況 |
|---|---|---|
| `true` | 0/3,553 | 判分檔的 try 數和 try 檔數不同，這份快照沒有出現 |
| `false` | 1,302/3,553 | 有 try 且已判分的程式題，兩者相同 |
| 沒有這個鍵 | 2,251/3,553 | 沒有 try 檔的程式題 922 筆、有 try 的照片題 1,293 筆、沒有 try 的照片題 36 筆。照片題沒有判分檔，所以不比 |

### Q10：用原判還是重判，重判結果能不能提供
