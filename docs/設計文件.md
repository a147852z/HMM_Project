## 1. 這個專案在做什麼

本研究的主體是 **K（HMM 知識核心）**。它位於智慧分散式 ERP 架構的中央：

```text
A（ERP 生成）──場域案例──▶ ┌──────────── K ────────────┐ ◀──操作紀錄／AoV 演變── C（Playwright 蒐集）
                           │ 資料：累積各場域的演變序列 │ ◀──案例資料── CVflow、硬體生成（RTL）
A ◀──領域知識回饋────────── │ 模型：每個場域訓練 HMM     │
                           │ 知識：汲取、表達、累積      │
工廠 AP ◀──HMM 協助 AoV 生成 └───────────────────────────┘
（AP-UT 不錄製；AP-D、AP-K 納入 C 的蒐集）            C ──操作需求──▶ H（HiBA 派工）──▶ 工廠 ERP
```

**一次演變序列**：工廠收到一張製令後，ERP 產生工作流程 AoV。人員檢視流程，每修改一次就產生一個修改事件，直到確認定案。這一連串修改就是一條序列。同一個場域累積許多序列，再拿來訓練該場域的 HMM。

**K 的兩個用途**：(1) 把領域知識提供給 A，協助建立 ERP；(2) 用 HMM 協助工廠 ERP 生成 AoV，結果交人員確認。

## 2. 已確定的設計決定

| 決定 | 內容 |
| --- | --- |
| 專案形態 | 新建 `k_core/`，與 `erp_hmm_simulator/` 平行；舊平台凍結保留作參考 |
| HMM 實作 | 用 hmmlearn `CategoricalHMM` 訓練（Baum-Welch），再轉成自寫推論模型做解碼、預測與視覺化，並以測試確認兩邊似然一致 |
| AoV 結構 | **有向無環圖（DAG）**；驗證節點識別唯一、連線端點存在、無自我迴圈、無循環 |
| 修改原因 | 選填。工作人員寫的標記 `reason_source="human"`，LLM 補寫的標記 `"llm"`，修改者（人或 AI 代理人）當時自己記錄的標記 `"actor"`；沒有原因就保留缺值 |
| 修改者類型 | `human`、`system`、`synthetic`、`ai_agent`（例如 CVflow 中由大模型設計流程圖） |
| 隱藏狀態 | 數量由 BIC／AIC 選擇；名稱使用中性編號 `H0`、`H1`…，語意要經過人工解讀 |
| 案例的定義 | **一個案例 = 一種領域／一個廠商／一種資料類型**。同一案例內的不同參與者（工作人員、AI 模型）記為屬性，不另開案例 |
| 資料 | 工廠真實案例尚未取得。已使用 **CVflow 真實資料**（佳元實驗材料包：5 個 AI 模型解 41 題影像辨識題的逐輪流程圖）測試，結果見 `docs/CVflow實驗報告.md`；另有標記的示意資料用來驗證程式 |
| 已結構化資料 | 已經是結構化 JSON 的來源（例如 CVflow）用程式轉接器直接轉換，不經 LLM |
| 通用性 | 系統會用在很多不同場域，**原始資料格式不固定** |
| 原始資料轉換 | 在 K 系統內呼叫**本地 LLM**，把原始資料整理成固定 JSON 格式。透過 OpenAI 相容網址呼叫，參考 LM Studio 的用法（例如 `http://localhost:1234/v1`） |
| 提示詞 | **每個案例使用各自的分析提示詞**。提示詞每次修改都保留成新版本，可以追溯每筆資料是用哪一版整理的 |
| 人工確認 | LLM 的轉換結果要先經人工確認，核准後才進入訓練資料 |
| LLM 與程式的分工 | LLM 只負責理解內容。識別碼產生、版本差異計算、修改類型推定、DAG 檢查、原因出處核對，都由程式處理 |

## 3. 不可違反的規則

1. **場域隔離**：每個場域分開匯入、訓練與取用模型。CVflow、硬體案例不會自動併入工廠模型。
2. **序列邊界**：多條序列一起訓練時，要提交「合併觀測＋各序列長度」，不可把上一條的結尾接到下一條的開頭。
3. **只用當時可得的資訊**：即時推論只能使用已發生的事件前綴。示意資料的標準答案、修改原因、最終流程都不能進入觀測。
4. **原始與衍生分開**：原始事件完整保存；特徵與模型都是衍生資料，編碼規格改版後可以重新產生。
5. **誠實回報**：資料不足、沒有模型、沒有合法候選時，回傳明確狀態。模型分數不可稱為成功率；示意資料的結果不可說成真實工廠成效。
6. **可重現**：訓練、示意資料與資料切分都要固定種子並記錄設定。

## 4. 系統架構（`k_core/backend/kcore/`）

| 模組 | 對應規格的元件 | 責任 |
| --- | --- | --- |
| `database.py` | 資料層 | 場域、序列、修改事件、AoV 快照、訓練工作、模型版本（SQLite） |
| `aov.py` | 結構驗證器 | DAG 驗證、套用修改差異、計算結構特徵 |
| `service.py` | CaseRegistry、DataIngestion、SequenceBuilder、ModelRegistry、InferenceService | 匯入、去重、定案重建、訓練流程、版本管理、推論 |
| `encoding.py` | FeatureEncoder | 事件轉成觀測符號；編碼規格有版本號；不認得的符號歸為 `__UNK__` |
| `hmm/training.py` | HMMTrainer | hmmlearn 訓練、多次重跑、用 BIC 選 K |
| `hmm/model.py` | 推論核心 | 前向（縮放）、後向、後驗、維特比、下一觀測預測 |
| `hmm/hybrid.py` | 結合預測 | HMM＋上一次修改：各半平均（預設）、依路線分轉移表；都隨模型版本保存 |
| `evaluation.py` | 評估 | 困惑度、下一觀測 Top-1/3、MRR、unigram／bigram 基準、示意標籤配對 |
| `synthetic.py` | 示意資料 | 產生埋入 3 個潛在階段的 AoV 演變序列 |
| `conversion/` | DataIngestion（原始資料） | LLM 轉換設定（提示詞版本）、原始文件、呼叫本地 LLM、草稿驗證、人工審核、核准後匯入 |
| `adapters/cvflow.py` | DataIngestion（已結構化資料） | CVflow 逐輪流程圖 → 演變序列；節點改名對齊、多 port 連線合併、執行結果與修改者理由 |
| `api.py` | 介面 | `/api/v1/cases/...`（規格書第 11 節） |
| `k_core/frontend/` | 研究頁面與審核畫面 | React＋Vite＋MUI；模型研究（模型概況、隱藏狀態、序列重播）、轉換設定、原始文件、轉換與審核 |

**LLM 轉換流程：**

```text
上傳原始文件（文字；UTF-8／Big5 自動判斷）
  → 選擇案例的轉換設定（網址、模型、案例提示詞＋K 固定格式說明）
  → 本地 LLM 輸出 JSON 草稿（要求結構化輸出）
  → K 驗證：格式、DAG、版本差異、原因出處；由程式產生識別碼
  → 待審核：審核者可直接修正草稿，修正後重新驗證
  → 核准：匯入並定案，每條序列都記錄文件、提示詞版本、模型、審核人
```

LLM 可用兩種方式描述一次修改：直接寫出差異（`change`），或給出修改後的完整流程（`after_workflow`）。後者由程式精確算出差異，較不容易出錯。

修改原因標記為 `human` 時，引用的原因文字必須能在原文中逐字找到，否則自動降為 `llm` 並提示審核者。

同一份文件重新轉換時，產生的序列識別碼不變，因此不會重複計入訓練資料。

**觀測編碼（fs-v1 預設）**：`修改類型|受影響活動類型`，例如 `insert_activity|inspect`。可選欄位還有 `node_delta`、`edge_delta`。

### 5.1 已完成 ✅（規格書第 13 節的階段 1、2）

| 功能 | 說明 |
| --- | --- |
| 場域登記 | `erp`／`cvflow`／`hardware`／`other`；可設定是否錄製 |
| 演變序列匯入 | 建立序列（初始 AoV）→ 批次提交事件 → 定案；事件可以不按順序到達 |
| 去重與一致性 | 同一事件重送算作重複；同 ID 但內容不同會被拒絕；順序缺號、版本鏈不連續、修改後出現循環，都會擋下定案並列出原因 |
| AoV 重建 | 定案時從初始流程逐步套用修改，保存每個版本的完整快照 |
| 特徵編碼 | 有版本號的編碼規格；未見符號歸為 `__UNK__`；可設定稀有符號門檻；可用活動類別對照表把細的活動類型歸成粗類別 |
| CVflow 轉接器 | 整批 CVflow 資料為一個案例 `CVFLOW`（五個 AI 模型合併，模型名稱為屬性），155 條序列、719 次修改；HMM 選出 K=2（兩條解題路線），結果見 `docs/CVflow實驗報告.md`。腳本：`k_core/backend/scripts/cvflow_merged.py`（另有分模型對照 `cvflow_experiment.py`、交叉驗證 `cvflow_cv.py`） |
| 非監督式訓練 | hmmlearn 多序列訓練、拉普拉斯平滑、多次重跑、用 BIC／AIC 選 K；依時間切分訓練與測試序列 |
| 模型版本 | 保存參數、編碼規格與指標；可切換使用中的版本；重啟後重新載入，推論結果相同 |
| 推論 | 對任一序列前綴輸出每步信念、維特比路徑、下一觀測 Top-k；同時記錄模型版本、編碼版本與使用的預測方法（預設 HMM 與 bigram 各半平均，可指定只用 HMM 或路線轉移表） |
| 評估 | 對保留的測試資料計算困惑度、Top-1/3、MRR，並比較 HMM、兩種結合方法、unigram、bigram；示意資料另外計算潛在階段配對準確率 |
| LLM 轉換與審核畫面 | 前端（`k_core/frontend`，埠 5174）可以管理轉換設定、上傳文件、開始轉換，並逐步審核：原文標示依據與引文、AoV 版本變化圖、檢查結果、草稿修正、核准或退回。後端：轉換設定與提示詞版本、文件上傳（自動判斷 UTF-8／Big5）、連線與模型檢查、背景轉換、草稿驗證、審核者修正、核准或退回、來源追溯 |
| 研究頁面 | 模型研究分頁：比較各預測方法的測試指標、解讀隱藏狀態（含依 AI 模型與成敗分組）、逐步重播序列並比較各方法預測與實際修改；後端 `/replay`、`/analysis` |
| 測試 | 57 個 pytest 測試，對應規格書第 14 節驗收條件 1～5、8～10、12，以及 LLM 轉換流程（用模擬的 LLM 測試） |

**示意資料驗證結果**（200 條序列，K 從 2 到 5）：
- BIC 選出 K=3，與埋入的潛在階段數相同。
- 潛在階段配對準確率 96%。
- 自寫推論與 hmmlearn 的似然差距為 0。
- 測試集困惑度：HMM 5.93、bigram 6.36、unigram 7.41。
- 下一觀測 Top-1 HMM 為 35%，**低於 bigram 的 39%**。

HMM 在機率估計上優於基準，但單看第一名預測還沒有贏。真實資料進來後要持續觀察這一點。

## 7. 舊系統：ERP HMM 模擬平台（凍結）

`erp_hmm_simulator/` 是先前的研究原型：用模擬器產生「使用者操作 ERP 畫面」的資料，推論操作階段並預測下一步。它提供 8 個網頁頁面與 25 個測試，詳見其 README。

這個平台不再擴充。它的 HMM 推論程式已經移植到 `k_core`，並修正了後向演算法的縮放方式與未知觀測的處理；React Flow 編輯器之後可作為 K 前端的參考。
